# Promolux Technical Admin · Laravel Pulse

## Назначение и адреса

- \`https://soleyev.uz/promolux/tech\` — вход с тремя карточками.
- \`https://soleyev.uz/promolux/tech/login\` — отдельная авторизация через Filament.
- \`https://soleyev.uz/promolux/tech/pulse\` — Laravel Pulse в новой вкладке (после установки).
- Telescope и Nightwatch в первом этапе не устанавливаются; карточки не ведут на пустые URL.

Роль \`tech_admin\` может входить только в техническую панель. Активный \`owner\` допускается как резервный администратор. Остальные роли закрыты. Доступ к Pulse контролируется серверным Gate \`viewPulse\`; не полагаться только на скрытие карточки.

Техроль создаётся только по защищённой CLI-команде, не через бизнес-формы:

\`\`\`bash
php artisan crm:tech-admin <email>
\`\`\`

Подставьте принадлежащий администратору email. Пароль (не менее 12 символов) вводится скрыто, не передаётся аргументом командной строки, не хранится в файле.

## Установка Pulse — сначала в отдельной ветке и тестовой среде

Код роутов, авторизации и конфигурация в этом изменении подготовлены. **Сам пакет laravel/pulse пока не добавлен в composer.lock**. Нельзя добавлять зависимость только в composer.json без регенерации lock: production использует \`composer install\` по lock.

На машине разработки с Composer 2 и соответствующей версией PHP:

\`\`\`bash
composer require laravel/pulse
php artisan vendor:publish --tag=pulse-migrations
php artisan route:list --path=tech
\`\`\`

Проверить и включить в тот же Pull Request обновлённые \`composer.json\`, \`composer.lock\`, опубликованные миграции. Не публиковать полную конфигурацию Pulse поверх \`config/pulse.php\`: здесь уже установлены путь и хранение. В случае несовместимости пакета остановиться, не использовать \`--ignore-platform-reqs\`.

Изолированная тестовая база: выполнить миграции, \`php artisan test\` и проверки приватности /tech и /tech/pulse. Перед production необходимы отдельный review миграций, снимок базы, проверка свободных байт и inodes, безопасный релиз и ручная приёмка. **Никаких миграций и изменения production без одобрения.**

## Хранение и нагрузка

\`config/pulse.php\` устанавливает \`PULSE_STORAGE_KEEP=14 days\` и \`PULSE_INGEST_KEEP=14 days\` (по умолчанию). Pulse выполняет выборочную автоматическую очистку при сборе событий, поэтому это срок хранения, а не обещание удаления каждой записи с секундной точностью. Отсутствие трафика может задержать очистку. Проверить реальный рост таблиц за первые дни.

Использовать стандартный database storage и storage ingest без Redis и постоянного worker-процесса. Карточка ресурсов сервера требует \`php artisan pulse:check\`; на aHost Micro её **не включать**, пока провайдер не подтвердит допустимость долгоживущего процесса.

Для реального production выставить в \`shared/.env\` (если не наследуются значения по умолчанию) \`PULSE_PATH=tech/pulse\`, \`PULSE_STORAGE_KEEP="14 days"\` и \`PULSE_INGEST_KEEP="14 days"\`. Убедиться, что \`APP_DEBUG=false\`, \`SESSION_PATH=/promolux\`, HTTPS и приватный доступ сохранены. Никаких внешних сервисов Pulse не требует.

## Приёмка

1. Без авторизации \`/tech\` переводит на \`/tech/login\`, Pulse не открывается.
2. Роль \`tech_admin\` открывает \`/tech\` и \`/tech/pulse\`, но получает 403 на \`/crm\`; неактивная роль запрещена.
3. Роли manager, rop, cashier, designer не открывают ни хаб, ни Pulse.
4. Pulse открывается в новой вкладке; Telescope и Nightwatch не запускаются.
5. Проверить, что события создаются, время/SQL отображаются, нет утечек запросов и конфиденциальных данных.
6. В cPanel через несколько дней измерить размер \`pulse_*\` таблиц и inodes. Не запускать долгоживущий \`pulse:check\` на Micro без разрешения.
