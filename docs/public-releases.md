# Публичные релизы

Публичная история начинается с самостоятельного снимка 0.3.1. Не добавляйте приватный репозиторий как remote, не выполняйте merge, fetch, cherry-pick, push --mirror или копирование `.git` из него. Исходные коммиты и данные остаются приватными.

Для каждого релиза:

1. В приватном проекте завершите изменения отдельным коммитом. Проверьте чистое состояние; зафиксируйте его SHA в приватном журнале релизов.
2. Создайте временный пустой каталог вне обоих репозиториев. Из `git ls-files` переносите только app, bootstrap, config, database, resources, routes, tests; из public — только index.php, .htaccess, favicon.ico, robots.txt; из storage — только .gitignore. Из корня — artisan, composer.json/lock, package.json/lock, phpunit.xml, vite.config.js, .editorconfig, .gitattributes и безопасный .env.example. Не переносите целиком директории файловой системой.
3. До переноса в публичную ветку удалите персональные значения SetupOwner; проверьте новые файлы вручную. Сохраните публичные README, AGENTS, deploy-инструкции, защитные правила и исправления подпапки. Сравните изменения с последним экспортом; не затирайте публичные исправления старой приватной версией.
4. В отдельной ветке `codex/release-*` публичного репозитория примените проверенный файловый diff. Удаления рассматривайте отдельно. Миграции и финансовые сервисы требуют отдельного внимания. Сопоставьте хеши неизменяемых финансовых файлов.
5. В изолированном проверочном каталоге установите зависимости строго по lock (`composer install`, `npm ci`), проверьте тестовую конфигурацию, выполните все тесты Pest и сборку с ASSET_URL. Скопируйте только полученный public/build в публичную ветку. Проверьте отсутствие карт исходников и секретных VITE-переменных. Генерируемые Filament-ресурсы создаст composer install на хостинге.
6. `git add` только выбранные файлы; `git diff --cached --check`; `python tools/check-public.py`. Проверьте diff, список файлов и адрес автора коммита вручную. Скрипт сканирует также всю доступную историю, но не доказывает отсутствие всех возможных секретов.
7. Сделайте локальный коммит и повторите сканирование истории. Проверьте `git remote -v`, `git log --all` и отсутствие приватных веток/тегов. Для первого выпуска должен быть ровно один коммит, без родителей. После отдельного разрешения владельца можно создать Public GitHub repo и отправить только выбранную ветку.
8. Перед ручным Deploy HEAD Commit выполните приёмку и резервное копирование. Никогда не настраивайте автоматический push в cPanel или cron-деплой.

Версия изменяется только при согласованном релизе. Этот экспорт сохраняет 0.3.1. Коммиты публичного репозитория содержат публичный адрес автора; нейтральная локальная идентичность первоначального снимка не является GitHub-аккаунтом владельца.
